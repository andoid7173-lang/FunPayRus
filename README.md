## 🚀 Установка на чистый VPS (Ubuntu 22.04/24.04)

Рекомендуется отдельный тестовый сервер с Ubuntu 22.04/24.04 и `systemd`. Скрипты проверены по исходному коду; установка на реальном VPS ещё не подтверждена. Перед запуском прочитайте [`install.sh`](install.sh). Бот работает через исходящие HTTPS-запросы, открывать веб-порты для него не нужно.

**Шаг 1.** Создайте Telegram-бота через [@BotFather](https://t.me/BotFather): команда `/newbot`. Сохраните токен в личном менеджере паролей. Узнайте свой **числовой Telegram ID**, а не `@username`. Не отправляйте токен или Golden Key в ChatGPT, GitHub или чужие боты.

**Шаг 2.** Подключитесь к VPS по SSH, заменив IP на адрес сервера:

```bash
ssh root@IP_ВАШЕГО_VPS
apt-get update && apt-get upgrade -y
apt-get install -y ca-certificates git python3
git clone https://github.com/andoid7173-lang/FunPayRus.git /opt/funpayrus
cd /opt/funpayrus
```

**Шаг 3.** Если PR версии 0.3.4 ещё не объединён с `main`, переключитесь на ветку тестирования перед установкой:

```bash
git switch feature/manual-order-review-v034
python3 -m unittest discover -s tests -v
```

После объединения PR переключать ветку не требуется: достаточно `main`. Не используйте тестовую ветку для реальных продаж без отдельной проверки интеграции и правил площадки.

**Шаг 4.** Запустите установщик на VPS:

```bash
sudo bash install.sh
```

Скрипт попросит Telegram Bot Token (скрытый ввод) и Telegram Admin ID, создаст системного пользователя `funpayrus`, службу `systemd`, конфигурацию в `/etc/funpayrus/` и данные в `/var/lib/funpayrus/`. Для смены Telegram-токена: `cd /opt/funpayrus && sudo bash install.sh --reconfigure`.

**Шаг 5.** Откройте свой Telegram-бот, нажмите Start и отправьте `/start`, затем `/ping`, `/diagnostics` и `/setup`. Если бот не отвечает, проверьте службу:

```bash
sudo systemctl status funpayrus --no-pager
sudo journalctl -u funpayrus -n 40 --no-pager
```

**Шаг 6 (необязательно).** Для тестового соединения со своим FunPay-аккаунтом введите Golden Key **только в защищённом терминале VPS**:

```bash
cd /opt/funpayrus
sudo bash scripts/configure_funpay.sh
sudo systemctl restart funpayrus
```

В личном Telegram-чате проверьте `/funpay`. Мониторинг активируется через `/orders on`, уведомления включаются отдельно в `/notifications`. HTML-парсер работает только с первой страницей списка продаж; он может ошибаться, а его `paid` **не является достоверным подтверждением оплаты**.

### Очередь ручной проверки

- `/queue` показывает локальные заявки, которые HTML-мониторинг считает предположительно оплаченными, включая записи с первого успешного опроса.
- Кнопки ведут на официальные страницы заказов. **Проверьте оплату и условия сделки на FunPay самостоятельно.**
- После самостоятельного исполнения заказа владелец может отправить `/queue done НОМЕР_ЗАКАЗА`. Это **только отметка в локальном SQLite**, а не отправка товара покупателю.
- Администраторы могут смотреть очередь, но не отмечать выполнение. `closed` и `refunded` блокируют необработанную запись, но парсер по-прежнему экспериментальный.
- Автовыдача, автоответы, Steam Guard и операции с аккаунтами отсутствуют. Для работы с реальными продажами необходимы отдельная проверка источника оплаты, надёжности интеграции и правил площадки.

### Конфигурация и безопасность

Секреты хранятся только на VPS в `/etc/funpayrus/bot.env` и `/etc/funpayrus/funpay.env` с ограниченными правами. Заказы и настройки находятся в `/var/lib/funpayrus/`. Не коммитьте эти файлы, не публикуйте журналы с личными данными и создавайте резервные копии. Для безопасной повторной настройки используйте интерактивные скрипты — не вставляйте токены в текст команд с историей оболочки.

### Обязательная ручная проверка перед резервированием (v0.3.7b1)

Полученное от другой нейросети `funpayrus_core` протестировано отдельно, но **не заменяет существующий бот**: его таблицы `core_*` не совместимы с текущей схемой, а возврат зарезервированного кода на склад при отмене небезопасен, если код уже показывали человеку. Из его подходов в FunPayRus перенесены явная проверка оператором и необратимый журнал основных действий.

Перед первым резервированием цифрового товара:

1. Открой заказ на официальном сайте FunPay и лично проверь фактическую оплату, покупателя, отсутствие возврата и условия сделки.
2. В приватном Telegram-чате **владельца** отправь `/verify НОМЕР_ЗАКАЗА`. Команда только записывает твоё решение в SQLite, **не подтверждает оплату через официальный API**.
3. Зарезервируй через `/stock reserve НОМЕР_ЗАКАЗА GAMEKEY`, извлеки код на VPS и отправь покупателю вручную согласно разделу ниже.
4. Заверши через `/stock issue НОМЕР_ЗАКАЗА`. Историю действий (ручная проверка, резерв, выдача, списание и отзыв проверки) покажет `/audit НОМЕР_ЗАКАЗА`. В аудите нет содержимого цифрового товара.

**Без /verify резервирование теперь запрещено.** Повторная проверка идемпотентна. При обнаруженном `closed` или `refunded` ручная авторизация отзывается и выполнение блокируется. Зарезервированный код **никогда не возвращается на склад автоматически**: его могли уже показать. В спорной ситуации владелец вправе окончательно списать резерв командой `/stock void НОМЕР_ЗАКАЗА`.

Старые базы сохраняются, создаются только новые таблицы `manual_verifications` и `order_action_audit`. Старые записи **не считаются проверенными** и требуют новой ручной проверки перед будущим резервированием. Автоматических отправок покупателям нет.

### Локальный склад и ручная выдача кодов

Склад добавлен для цифровых товаров, которые продавец **имеет право продавать и передавать**. Файлы с кодами не отправляются в GitHub. Учёт кодов хранится в `/var/lib/funpayrus/orders.sqlite3` (SQLite с правами 0600). **Коды не выводятся в Telegram**. Ключи входа Steam, пароли, данные платёжных карт и коды двухфакторной аутентификации не загружайте в склад.

1. Вначале установите и запустите бот. Затем на VPS добавьте цифровой код в SKU (имя товара, например `GAMEKEY`). Используйте личный SSH-терминал с отключённой записью сеанса:

```bash
cd /opt/funpayrus
sudo -u funpayrus python3 -m bot.stock_cli add GAMEKEY
sudo -u funpayrus python3 -m bot.stock_cli list
```

Команда `add` попросит код через скрытый ввод — **не вставляйте код прямо в команду**. `list` выводит только количество доступных, зарезервированных, выданных и списанных единиц.

2. В личном Telegram-чате владельца включите мониторинг `/orders on`. Получив уведомление, **самостоятельно проверьте оплату и условия заказа в FunPay**, затем выполните `/verify НОМЕР_ЗАКАЗА` и только после этого резервируйте товар:

```text
/stock
/stock reserve НОМЕР_ЗАКАЗА GAMEKEY
```

3. На VPS в личном SSH-терминале откройте зарезервированный код:

```bash
cd /opt/funpayrus
sudo -u funpayrus python3 -m bot.stock_cli show НОМЕР_ЗАКАЗА
```

**Не записывайте этот вывод в общий журнал терминала.** Выдайте код покупателю вручную *только после достоверной проверки оплаты* непосредственно в разрешённом канале FunPay. Бот не отправляет сообщение, код или аккаунт покупателю.

4. После успешной ручной передачи отметьте факт выдачи:

```text
/stock issue НОМЕР_ЗАКАЗА
```

Это переводит зарезервированный код в `issued` и закрывает локальную задачу проверки. Повторно тот же код не выдаётся. Если заказ отменён, код уже был показан или возник спор — безопасно вывести код из обращения через `/stock void НОМЕР_ЗАКАЗА`; он не вернётся на склад. Состояние `void` необратимо. Не используйте `/queue done` для заказов с зарезервированным кодом: их завершает `/stock issue`.

**Ограничения:** это локальный инвентарь и ручная выдача, а не автономный магазин. Тесты проверяют код без реального соединения FunPay, авторизацию и системный сервис на VPS пока нужно проверять отдельно. Никакая внешняя лицензия или официальный API FunPay этим не предоставляется.


## Управление заказами, заметки и платформы (v0.3.5b1)

Новые функции доступны **только владельцу** через личный чат с Telegram-ботом:

- `/stats` — локальная сводка наблюдений: статусы заказов, очередь проверки, склад и непереданные уведомления. **Это не достоверная статистика платежей или выручки.**
- `/note НОМЕР_ЗАКАЗА текст` — сохранить рабочую заметку к уже обнаруженному заказу. `/note НОМЕР_ЗАКАЗА` — посмотреть. `/note clear НОМЕР_ЗАКАЗА` — удалить. Не храните в заметках пароли, email-адреса, резервные коды и персональные данные.
- `/lowstock` — показать SKU с остатком не выше порога (по умолчанию 3). `/lowstock set GAMEKEY 2` — изменить порог для существующего SKU. Список остатков пока открывается вручную; автоматическая периодическая рассылка не включена.
- `/platforms` — экран центра уведомлений платформ. В v0.3.5 он **не подключён ни к одному почтовому ящику** и не мониторит Outlook самостоятельно.

### Защищённая модель почтовых интеграций

Модуль `bot/mail_events.py` — встроенный в приложение (не запускаемый сторонний Python-плагин). Он принимает только тип события, название платформы, поставщика и дату. В базе хранится HMAC-отпечаток идентификатора сообщения для защиты от дубликатов; сырой ID, адрес, тема, тело, вложение и одноразовые коды не сохраняются.

Сейчас **нет реализации OAuth-авторизации, запроса к Microsoft Graph или Gmail API, фонового polling, автоматического чтения почты или извлечения кодов**. Не добавляйте пароли Outlook, Steam, OAuth-токены или Steam Guard-коды в `.env`, GitHub, Telegram и команды бота.

Для будущего Outlook-адаптера используйте пользовательскую OAuth-авторизацию с минимальными read-only разрешениями (проверить актуальные требования Microsoft Graph, включая доступность `Mail.ReadBasic` для типа учётной записи), строгий allowlist ресурсов Microsoft, защиту токенов, ручное отключение и отзыв согласия. Содержимое писем, коды входа и ссылки подтверждения не должны попадать в FunPayRus. Для Gmail или другого провайдера реализация отдельно оценивает права и условия API; ни одна интеграция не активируется по умолчанию.

Steam, Epic Games, EA, Ubisoft и другие игровые платформы рассматриваются как **метки безопасных уведомлений о событиях**. Никакие входы, обход 2FA, выдача аккаунтов или подтверждение операций от лица пользователя не выполняются.

## 🕹️ Управление службой

```bash
# Статус
sudo systemctl status funpayrus --no-pager

# Перезапуск
sudo systemctl restart funpayrus

# Остановка / запуск
sudo systemctl stop funpayrus
sudo systemctl start funpayrus

# Последние сообщения журнала
sudo journalctl -u funpayrus -n 40 --no-pager
```

Если бот не отвечает, начните с проверки статуса и журнала. **Не публикуйте полный журнал без проверки на наличие личных данных.**

Программа ищет плагины в двух местах:

```text
/opt/funpayrus/plugins/       # Плагины, включённые в сам проект
/var/lib/funpayrus/plugins/   # Личные плагины пользователя
```

Пример структуры пользовательского плагина:

```text
plugins/
└── my_plugin/
    ├── manifest.json
    └── plugin.py
```

Пример `manifest.json`:

```json
{
  "name": "Мой плагин",
  "version": "0.1.0",
  "description": "Пример команды",
  "command": "myplugin",
  "enabled": true
}
```

Пример `plugin.py`:

```python
def handle(args: str) -> str:
    return "Плагин работает! 🐱"
```

В v0.3.1b1 внешние плагины по умолчанию **не исполняются**. Разрешение `FUNPAYRUS_ALLOW_EXTERNAL_PLUGINS=1` допустимо только после проверки кода плагина. Подробнее в [SECURITY_TEST_RELEASE.md](SECURITY_TEST_RELEASE.md).

После добавления плагина вручную перезапустите службу:

```bash
sudo systemctl restart funpayrus
```

Команда `/plugins` покажет обнаруженные плагины, а кнопки позволят включать и отключать их. Настройки переключателей записываются в `/var/lib/funpayrus/plugin-state.json` и не должны пропадать при обновлении исходного кода.

> [!CAUTION]
> **Python-плагин — это исполняемый код.** Он может получить доступ к файлам и секретам, доступным процессу бота. Устанавливайте только проверенные плагины. Загрузка ZIP, установка из ссылки и песочница для стороннего кода **пока отсутствуют**.

## 🔄 Обновление из GitHub

```bash
cd /opt/funpayrus
sudo bash scripts/update.sh
```

Скрипт проверяет наличие изменений, показывает новый Git-коммит, запрашивает подтверждение и перезапускает службу. **В тестовой версии добавлены резервное копирование и откат Git-кода после неудачной проверки.** При этом скрипт `scripts/update.sh` рассчитан **только на `main`** и не используется для переключения бета-веток. Для приватного репозитория Git-доступ должен работать и в контексте пользователя, от которого запускается скрипт.
