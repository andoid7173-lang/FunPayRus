# Спецификация встроенного центра платформ (v0.3.5, этап 1)

## Источник

Пользовательский файл `confirm_reminder.py` для **FunPay Cardinal** — модуль отложенного напоминания о подтверждении заказа, а не реализация Steam/Outlook. Его сторонний код в проект не копировался и не исполнялся. Возможные идеи (очередь, лимит частоты, изменения статуса) требуют собственной реализации и проверки.

## Реально реализовано

- `bot/mail_events.py` — встроенный в FunPayRus интерфейс безопасного журнала событий электронной почты. Принимает только `provider`, `platform`, `kind`, `opaque_id`, `received_at`; сохраняет HMAC-отпечаток ID (при наличии отдельного уникального секретного ключа), типы события и время.
- `/platforms` — экран состояния, доступный только владельцу. Пока показывает «не подключено» и количество ранее внесённых метаданных.
- `/stats`, `/note` и `/lowstock` — учёт заказов и остатков без дополнительных прав доступа к внешним платформам.

**Outlook / Gmail / Steam / Epic / EA / Ubisoft / Battle.net / GOG пока НЕ подключены.** Отдельный OAuth-адаптер, фоновая проверка почты, Microsoft Graph, Gmail API и отправка уведомлений о новых письмах **не реализованы**.

## Требования к будущему Outlook-адаптеру

1. Использовать *собственную* учётную запись пользователя и официальную OAuth-авторизацию через Microsoft identity platform с MSAL; не принимать email-пароли, не подделывать страницу входа, не запрашивать или сохранять Steam Guard/2FA-коды.
2. Рассматривать delegated scope `Mail.ReadBasic` как верхнюю границу доступа при совместимости с типом учётной записи. По документации Microsoft он позволяет читать метаданные, но исключает body, bodyPreview и attachments. Не запрашивать `Mail.ReadWrite`, `Mail.Send`, application-wide права или доступ к общим ящикам без отдельного доказанного основания.
3. Получать только ограниченный набор полей сообщений (`id`, `receivedDateTime`, необходимые для классификации разрешённые заголовки). Не возвращать `subject` и `from` в Telegram, не сохранять их. Письма *могут быть поддельными*; адрес отправителя не является проверкой легитимности.
4. Никаких переходов по ссылкам в письмах, загрузок вложений, автоматических подтверждений Steam, смены паролей и передач цифровых кодов. Steam Guard выполнять только вручную на устройстве владельца.
5. Никакого подключения по умолчанию. Нужен явный `connect`, `disconnect/revoke`, уведомления о неуспешной авторизации и лог с редактированием секретов. Владелец должен видеть, что доступ выдан.
6. Хранить токены только в защищённом хранилище с правами минимум 0600 и шифрованием в покое, отдельным ключом; предусмотреть ротацию, изоляцию роли ОС и резервное копирование без передачи токенов в GitHub/Telegram. Восстановление доступа к серверу не должно означать автоматическую выдачу дополнительных разрешений.
7. Учитывать rate limiting, пагинацию, сроки годности токенов, отказы API, повторы и дубли. Первый запуск должен молча зафиксировать контрольную точку без рассылки всей истории.
8. Для Gmail или иных провайдеров — отдельные адаптеры с официальным API и минимальными разрешениями; если метаданные нельзя получить без чтения писем, указывать это пользователю и не выполнять интеграцию по умолчанию.
9. Тестировать пустой ящик, поддельные заголовки, тайм-ауты, 429, истёкший токен, повреждённую базу, отключение/отзыв доступа, повторный запуск, изоляцию чужих Telegram ID, отсутствие кода/пароля в логах.

## Модель угроз

- Компрометация VPS или прав администратора может раскрыть все доступные процессу секреты — **нулевой риск кражи гарантировать невозможно**.
- Письма-подделки могут имитировать Steam/другие платформы.
- Ошибки в интеграции могут дублировать уведомления, слишком часто опрашивать API и раскрывать персональные данные.
- Наличие нового письма ни при каких условиях не доказывает оплату FunPay и не авторизует выдачу товара.

До завершения проверки безопасности, официальных API и реального тестирования продакшен-адаптер должен оставаться отключённым.
